# I9: Docker Compose + netem or Containernet for the emulated backend

- **Issue:** #194 (I9). **Spec:** `docs/superpowers/specs/2026-11-03-onion-fl-infrastructure-design.md` §11.
- **Status:** decided, 2026-11-06. I10 (#195) implements the chosen option.
- **Raw data:** [`2026-11-06-i9-emulator-raw.jsonl`](2026-11-06-i9-emulator-raw.jsonl), one row per measurement.
  `python scripts/spike_netem/measure.py summarize docs/decisions/2026-11-06-i9-emulator-raw.jsonl` prints every table below in full.
- **Scripts:** `scripts/spike_netem/` (its README lists the exact commands).

## Decision

**Docker Compose + netem.** Both options meet every acceptance criterion with
almost identical numbers, because both end up as `tc netem` on veth interfaces
of the same kernel. Compose wins on what is left: it needs only `NET_ADMIN`,
uses standard Docker, and has no dependency on an unmaintained image.
Containernet stays a possible `emulators` plugin.

## Acceptance criteria (fixed before measuring, spec §11)

| Criterion | Threshold |
|---|---|
| Latency (RTT) | error ≤ 10 % of the target, or ≤ 1 ms |
| Bandwidth | error ≤ 10 % |
| Loss | error ≤ 1 percentage point |
| Isolation | saturating the other links moves a link's measurement by no more than the same error |
| Runs | on the development machine, or in a documented Linux VM |

## Setup

- **Host:** Windows 11 Pro, Intel Core i7-14650HX (16 cores, 24 threads), Docker Desktop 28.3.2 on WSL2.
  The kernel is `6.6.87.2-microsoft-standard-WSL2`, with `sch_netem`, `sch_tbf`, `sch_htb`, `ifb` and `openvswitch` built as modules.
- **Lab:** the same lab for both options: 1 cloud, 2 fogs and 4 edges, with 6 physical links (`scripts/spike_netem/links.json`).
  - Each edge has its own link to its fog, and each fog its own link to the cloud.
  - The targets were chosen to cover 2–50 ms one-way latency, 5–100 Mbit/s and 0.5–5 % loss.
- **Hosts:** every host is a container from `scripts/spike_netem/Dockerfile` (Debian bookworm-slim with `iproute2`, `iputils-ping`, `iperf3`, `procps`, `python3-numpy` and `net-tools`).
  - The Compose run used the image before `net-tools` was added (Containernet needs it, see below); the measuring tools were the same.
- **Option A, Compose:**
  - One container per host and one Docker bridge network per physical link, so each link is its own interface in each container.
  - `measure.py shape` applies `tc qdisc replace dev <if> root netem delay <L>ms rate <B>mbit [loss <p>%]` to both ends of each link, egress only.
  - The two-hop path e1 → fog1 → cloud uses static routes and `ip_forward` in the fogs.
- **Option B, Containernet:**
  - The official `containernet/containernet:latest` image, created 2021-07-14, with Ubuntu 18.04, Python 3.6.9, Open vSwitch 2.9.8 and Docker client 20.10.7.
  - It runs as a privileged container with `--pid=host`, the Docker socket, and the VM's `/lib/modules`.
  - `containernet_topo.py` builds the same lab as direct `TCLink`s between Docker hosts. Mininet shapes both ends with HTB for the rate and a netem child for delay and loss.
  - The routes are the same as in Compose.

## Method

`measure.py run` drives the containers with `docker exec`. Each measurement was
repeated 5 times. The two options were measured one after the other, never at
the same time. There were two shaping sets, so that no number needs a
correction:

- **`rate`: delay and rate, no loss.**
  - RTT: 100 pings 20 ms apart.
  - Bandwidth: TCP goodput from `iperf3` over 5 s, discarding the first second.
  - The target RTT is 2 × the one-way latency. The target bandwidth is the configured rate.
- **`loss`: delay, rate and loss.**
  - One-way loss from an `iperf3` UDP stream: half the link rate, 1200-byte datagrams, 5 s.
  - In each option, 3 of the 60 UDP tests exited with no result: iperf3's TCP control connection runs over the lossy link.
    Each was retried once, and the retry is logged on stderr.
  - A first Compose `loss` run, without the retry, stopped in its third repetition. It was discarded whole.
- **Cross traffic:**
  - For every link and repetition, the measurement is taken once alone and once while bulk TCP flows saturate the other 5 links.
  - The cross-traffic flows go from the lower to the upper end of each link: edge → fog and fog → cloud.
  - Isolation compares the two means.
- **CPU:** `cpubench.py` trains a 64-128-2 MLP with SGD in numpy, with 4 processes and one BLAS thread each, for 10 s.
  - The limits were 0.5, 1 and 2 CPUs: `docker run --cpus` for Compose, and `cpu_quota`/`cpu_period` on Containernet hosts.
  - The expected throughput is min(cpus, 4) × the 1-process throughput without a limit.

## Results: against the criteria

Each cell gives the worst case over the 6 links, alone and with cross traffic.

| Criterion | Compose + netem | Containernet |
|---|---|---|
| RTT error | +0.17 ms (+4.4 %, on the 4 ms link); ≤ +2 % on the others | +0.14 ms (+3.4 %, on the 4 ms link); ≤ +1.6 % on the others |
| Bandwidth error | −4.3 to −4.4 % on every link | −4.4 to −4.5 % on every link |
| Loss error | −0.51 pt (e4, 5 % target) | +0.55 pt (e4, 5 % target) |
| Isolation, RTT | −0.14 ms | −0.15 ms |
| Isolation, bandwidth | ±0.01 Mbit/s | +0.09 Mbit/s |
| Isolation, loss | +0.91 pt (e4) | +0.74 pt (e4) |
| Standard deviation between repetitions | RTT ≤ 0.21 ms, bandwidth ≤ 0.01 Mbit/s, loss ≤ 0.45 pt | RTT ≤ 0.22 ms, bandwidth ≤ 0.10 Mbit/s, loss ≤ 0.79 pt |
| Runs on Windows 11 + WSL2 (Docker Desktop) | yes; needs only `cap_add: NET_ADMIN` | yes, with workarounds (below) |
| **Meets all criteria** | **yes** | **yes** |

Reading the numbers:

- **The bandwidth bias is the same, about −4.4 %, in both options and on every link.**
  - It is TCP/IP header overhead: 1448 payload bytes per 1514-byte frame is 0.956.
  - Both shapers (netem `rate` and HTB) count Ethernet frame bytes, and iperf3 reports goodput.
- **The RTT bias, +0.1 to +0.5 ms, is the base veth/bridge latency plus timer granularity.**
  - In a 3-ping check before shaping, the RTT between two Compose containers was 0.075 ms.
- **The worst loss and isolation numbers are on e4 (5 % target), and they are sampling noise.**
  - A 5 s test at 2.5 Mbit/s sends about 1300 datagrams. The binomial standard deviation of a 5 % estimate is then about 0.6 pt, the same as the measured spread.
  - Both options pass, but the 1-point margin is tight at that loss rate. I12's calibration should use longer UDP runs.

- **The limits hold to within 7 % when a host runs alone, in both options.**
  - Both use the same mechanism, Docker's CFS quota.
- **Two limited hosts running at once each lose 12–16 % against running alone** (ratios 0.79–0.82 against the expected throughput).
  - Without any limit, the same pair loses 6–12 % (the control rows), so most of the drop comes from the laptop: turbo and P/E hybrid cores, shared by all containers.
  - The remaining 4–6 points come from the quota running 4 processes on 1–2 CPUs next to a neighbour.
  - **Consequence for I10 and I12:** calibrate `train_rate` with the hosts co-located as in the experiment, not one at a time. Pinning hosts to cores (`cpuset`) was not measured.
- **The concurrent test was run only through `docker run --cpus`.**
  - Containernet sets the same CFS knobs, so the result is expected to be the same, but it was not measured.

## Running on Windows 11 + WSL2

Both options run on Docker Desktop's WSL2 VM. Neither needs a separate Linux VM.

- **Compose:** it worked first time with `cap_add: [NET_ADMIN]`.
  - netem, tbf and IFB all load on demand from inside a container.
- **Containernet** needed the following workarounds:
  - **OVS kernel module.** Without `-v /lib/modules:/lib/modules:ro`, `ovs-ctl` cannot `modprobe openvswitch` (`Module openvswitch not found in directory /lib/modules/6.6.87.2-microsoft-standard-WSL2`), `ovs-vswitchd` never starts, and `ovs-vsctl add-br` hangs.
    The module is in the Docker Desktop VM; only the mount is missing.
  - **`ifconfig` in host images.** Mininet brings interfaces up with `ifconfig`, so a host image without `net-tools` gets DOWN links and no connected route (`Error: Nexthop has invalid gateway`).
  - **Import order.** `from mininet.link import TCLink` before `mininet.net` fails with a circular `ImportError: cannot import name 'Link'`.
  - **Privileges.** It needs a privileged controller container with `--pid=host` and the Docker socket: root on the Docker host.
  - **Old software.** The image is from 2021, with Python 3.6, Docker client 20.10.7 and OVS 2.9.8. It worked against Docker 28.3.2, but nothing pins that compatibility.
  - Mininet prints `*** Error` lines for each `tc qdisc del` on a fresh interface. They are harmless.
- **Not tried:** Docker Engine inside the `Ubuntu-24.04` WSL distribution, and a separate Linux VM. Neither was needed.

## Why Compose

1. **Fidelity is not what separates them.**
   - Every difference in the table is within the spread between repetitions.
   - Both shape with `tc` on veth pairs in the same kernel.
2. **Fewer privileges.**
   - Compose needs `NET_ADMIN` inside each host container.
   - Containernet needs a privileged container with the host's PID namespace and the Docker socket.
3. **Maintenance.**
   - The latest official Containernet image is from 2021 and runs Python 3.6. It needed three workarounds to run here.
   - Compose is standard Docker, and I10 can generate it from `Infrastructure`.
4. **Multi-hop topologies,** Containernet's advantage in the §11 table, did not matter here.
   - With direct links, Containernet also needed static routes.
   - Using OVS switches instead would add a switch hop per link without changing the shaping.

## Consequences for I10 (#195)

- **Networks:** one Docker network per physical link, with interfaces found by IP (`ip -4 -o addr show to <ip>/32`).
- **Shaping:**
  - netem `delay` + `rate` + `loss` on the egress of each end.
  - Different `bandwidth_up` and `bandwidth_down` map to different rates on the two ends.
  - Static routes for paths with several hops.
- **Bandwidth semantics:** decide whether `bandwidth` is the L2 link rate (what netem shapes; TCP gets about 95.6 % of it) and document it.
- **Queues:** netem's default queue is 1000 packets, 2.4 s at 5 Mbit/s.
  - A bulk transfer leaves a standing queue that delays everything after it on that link.
  - I10 should set `limit` from the link's bandwidth-delay product, or at least record it.
- **CPU:** `cpus` maps to `--cpus`. Calibrate with the hosts co-located (see CPU above).

## Not covered by this spike

The following were not measured:

- jitter and the `normal`/`lognormal` distributions;
- asymmetric up/down rates;
- `shared` versus `dedicated` links;
- live changes to a link (`network.schedule`, link down and up);
- rates above 100 Mbit/s;
- startup times;
- memory limits;
- an FL run on either option.
